# 形成当前 PRD

## 上下文契约

必读：当前任务的 `task.json`、用户原始需求，以及已有的 `prd.md`、`decisions.md`（若存在）。

按需读取：`AGENTS.md` 规范路由命中的文档、直接相关的项目索引、仓库说明、一个已有任务 PRD、为回答事实问题所需的少量源码或文档；UI 还原任务中只读取用户已选定且与当前问题直接相关的 Figma 节点或设计截图。

初始禁止：技术方案、实施方案、全部项目知识、无关任务、全仓库扫描，以及未选定范围的完整 Figma 文件、组件库和无关设计页面。

输出：保持当前事实和开放问题的 `prd.md`、追加式 `decisions.md`、必要的项目长期记忆更新，以及包含后续阶段建议的待确认需求摘要。

## 流程

1. 运行 `task status <task> --json`，确认任务仍在 `prd`；整理用户原始需求、已有 PRD、决策记录和直接相关的项目事实。UI 还原任务只确认纳入范围的页面、状态、目标视口、响应式范围和精确设计定位器；只有文件级 Figma 链接且无法确定有效 frame 时请用户选择，不读取整份设计稿猜测范围。完成：访谈主题、已知事实和当前需求变化已明确。
2. 判断澄清路径。目标、范围和验收口径已有充分事实时直接整理 PRD；存在少量必须由用户决定的未决项时调用一次 `grilling`，并让待决范围和完成标准覆盖实际缺口。问题需要设计证据时只读取与当前问题对应的精确节点，把事实摘要而非原始 Figma 响应交给 `grilling`；问题互相依赖、无法在当前上下文完整表述时读取并执行 [渐进探索](references/progressive-discovery.md)。完成：选择了与需求不确定性匹配的路径，没有为清晰需求安排访谈，也没有替用户决定真实取舍。
3. 创建或更新唯一的 `prd.md` 和追加式 `decisions.md`，不因惯例补造业务事实；同步本轮已经确认的长期记忆变化。在“约束与依赖”中用 inline code 写出本阶段实际读取的 `CONTEXT.md`、`adr/*.md` 或 `project/*.md` 根相对路径。完成：文档反映当前需求和开放问题，长期记忆与已确认结论一致。
4. 所有开放问题收敛后补齐完整 PRD 和稳定 AC ID，将“未决问题”写为“无”，并在当前任务的 PRD 与 decisions 中检查已解决 Q ID 不再被描述为待决条件。自行检查目标、范围、规则、异常和 AC 是否一致。完成：开放问题为零，AC ID 稳定，正文与决策记录不存在已解决问题残留。
5. 判断是否确实需要面向实施者之外人员的技术评审材料。API、数据库、安全、架构、跨系统协作或关键技术取舍是建议生成技术方案的强提示，但不是硬门禁；若 `spec.md` 足以承接实施且没有外部评审需要，建议跳过技术方案。完成：后续路径具有与外部评审需求对应的明确建议和理由。
6. 展示 PRD 关键结论和后续路径建议。确认问题必须写明文档、关键决定和目标阶段，例如“确认 `prd.md` 并跳过技术方案，进入 `implementation_spec`”。用户确认生成技术方案后进入 `technical_design` 并调用 `sw-technical-design`；确认跳过后直接进入 `implementation_spec` 并调用 `sw-spec`。完成：已按用户确认的唯一路径成功推进，或保留当前阶段等待明确确认。

## 文档规则

按下述文档规则创建并维护一份当前 `prd.md`。将原始需求与 grilling 结论合并成可读文本；需求变化时直接更新，历史交给 Git。探索状态只保存在“未决问题”中，不创建独立 map、ticket 或阶段；已解决问题的详细答案只保存在 `decisions.md`，PRD 正文只保留其形成的当前需求事实。

为每条验收标准分配稳定 ID，从 `AC-001` 开始。优先使用三级标题并写出可观察结果，例如：

```markdown
### AC-001 <可验证行为>

<前置条件、动作和预期结果>
```

不要在后续阶段重编号已确认 ID；删除或替代时在 `decisions.md` 记录原因。

UI 还原需求不把完整设计属性复制进 PRD。正文只保存实际范围所需的设计 URL 或 `fileKey + nodeId`、节点名称、设计版本（可获得时）、状态、目标视口、响应式范围和来源优先级；Figma 负责指定视口下的视觉事实，PRD 仍需明确设计稿无法表达的业务行为、异常、权限和无障碍要求。视觉 AC 不得只写“与 Figma 一致”，应能定位对应节点、状态和视口，但不为实施阶段抄录像素值。

## 决策记录

仅把影响范围、行为、兼容性或验收的关键选择追加到 `decisions.md`。每项写日期、关联 Q ID（若有）、决定、理由、影响；被替代时追加“取代哪项”，不改写旧记录。任务决定只有通过 `sw-domain-modeling` 的 ADR 三项门槛并取得用户确认后，才提升为项目级关键决策。

阶段命令按用户确认的路径二选一：

- `task phase <task> technical_design --confirmed`
- `task phase <task> implementation_spec --confirmed`
