# 编写实施 Spec

## 上下文契约

必读：`task.json`、`prd.md`、`decisions.md`、已确认的 `technical-design.md`。

按需读取：`AGENTS.md` 规范路由命中的文档、技术方案引用的 DDL、研究证据、目标代码符号和仓库运行说明。

初始禁止：其他任务、未引用的项目知识、无关源码、重复复制完整技术方案。

输出：唯一的 `spec.md`。

## 流程

1. 运行 `task status <task> --json`，确认任务处于 `implementation_spec`，读取已获用户确认的 PRD 和技术方案。完成：仓库范围和全部 AC 已知。
2. 将设计转换成唯一的 `spec.md`；引用设计章节和相关 ADR，不复制长篇内容。每个步骤写明仓库、修改点、依赖、验证、对应 AC 和停止条件；在“项目文档同步”用 inline code 列出本任务实际依赖、需要更新或复核的 `CONTEXT.md`、具体 ADR 和 `project/*.md` 路径。发现新的需求或技术取舍时停止编写，对必须由用户决定的事项调用 `grilling`，在当前请求中明确写出访谈主题、已知事实、待决范围和恢复编写所需的完成标准，更新并重新确认受影响的上游文档后再继续。完成：全部 AC 映射到可执行步骤和验证证据，长期记忆依赖及同步动作有明确落点。
3. 自行检查每个 AC 都有唯一实施落点、仓库顺序、验证方式和停止条件。任务很大时在 `spec.md` 内按顺序组织步骤，不维护独立 Slice 状态机。完成：方案可由后续会话从文档直接续做。
4. 向用户展示实施范围、顺序、测试策略、规则例外和未决风险。无阻塞且用户确认后进入 `implementation` 并调用 `sw-implement`。

进入 implementation 时让 CLI 自动记录每个仓库的 canonical root、branch、HEAD 和初始脏文件，不手工写 `task.json.git`。不在其他文档重复维护任务列表。规则或例外只在实质影响的步骤就地记录。

## 文档规则

创建并维护一份 `spec.md`。“测试与联调”按实施步骤写明验证方式；可稳定自动验证的代码行为默认 `TDD`，也可选择 `测试后补` 或 `替代验证`。TDD 写明通过公开接口观察行为的测试接缝、首个行为和验证命令，其他方式写明原因和替代证据。用户可明确让整个任务不使用 TDD，此决定只记录一次，无需在实施时重复确认。

可稳定隔离的新逻辑优先 TDD；UI 中的状态计算、校验和数据转换仍遵循该原则，布局、动画、复杂交互、遗留代码或缺少稳定测试接缝时可选择测试后补或截图、浏览器检查、人工验收等替代验证。本可测试却不写自动化测试的新逻辑必须随方案取得用户确认。

阶段命令：`task phase <task> implementation --confirmed`。实施中发现方案不成立时，先更新受影响的 PRD、技术方案、决策和 spec，再继续编码。
