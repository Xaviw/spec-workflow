# 编写实施 Spec

## 上下文契约

必读：`task.json`、`prd.md`、`decisions.md`。

按需读取：存在时读取已确认的 `technical-design.md`，只把其中的接口、数据、安全、架构和关键风险结论作为约束；同时按需读取规范、DDL artifact、目标代码符号、公共入口和仓库运行说明。UI 还原只读取确定当前实施边界所需的精确设计节点。

初始禁止：其他任务、未引用的项目知识、无关源码、重复复制完整 PRD 或技术方案。

输出：小任务只维护 `spec.md`；需要多个可独立实施单元时，维护总体 `spec.md` 和独立的 `slices/<序号>-<名称>.md`。

## 流程

1. 运行 `task status <task> --json`，确认 phase 为 `implementation_spec`，读取已确认 PRD、决定和可选技术方案。完成：仓库范围、全部 AC 和适用评审约束已知。
2. 判断是否需要 Slice。一个连续实施单元能覆盖全部范围时只用 `spec.md`；存在跨仓依赖、可独立验证的多个增量或后续会话无法只读取当前单元完成时，拆成有序 Slice。
3. 在 `spec.md` 写总体范围、仓库顺序、依赖、步骤或 Slice 索引、项目文档同步和完整 AC 映射。每个 AC 必须唯一指向一个步骤或 Slice；该实施单元必须实际写出主要验证证据，不能只在末尾映射表提及。
4. 不使用 Slice 时，每个步骤直接写范围、目标仓库和修改点、对应 AC、实施行为、验证命令与预期证据、停止条件。使用 Slice 时，将这些内容写入对应 `slices/*.md`，`spec.md` 只保留总体关系、顺序、进度和 AC 映射；Slice 不创建 CLI 命令、JSON 状态或独立 phase。跳过技术方案时，接口、数据库、安全、架构或跨系统协作中实施必须知道的决定直接写入对应步骤或 Slice，不另建替代设计文档。
5. 涉及公共 API、包导出、公共类型或多运行时入口时，对应步骤或 Slice 必须检查 `package.json#exports`、源码及运行时入口、生成声明和打包产物、消费者实际导入方式，以及正向类型消费和必要的负向兼容用例。技术方案只提供已评审契约，不替代本检查。
6. 验证命令只记录仓库根可执行的原生命令。根据仓库说明确认脚本或入口存在；只有命令名、工作目录或参数无法从仓库事实确定时才运行最小 smoke，不在 spec 阶段运行覆盖率、完整 E2E、完整构建或其他全量门禁。
7. 在请求确认前检查每个 AC、唯一实施落点和主要证据三者一致，Slice 顺序与依赖闭合，且实际引用的 `CONTEXT.md`、ADR 和 `project/*.md` 已在对应步骤就地列出。认证、授权、租户、身份和数据隔离 AC 必须在实施单元中安排动态负向证据，不能只依赖静态审查。发现需求或技术取舍变化时先同步并重新确认受影响上游文档。
8. 展示实施范围、顺序、测试策略、规则例外和未决风险。确认问题写明“确认 `spec.md` 的步骤或 Slice 顺序，进入 `implementation`”；用户明确确认后运行 `task phase <task> implementation --confirmed` 并调用 `sw-implement`。

## 测试方式

可稳定自动验证的代码行为默认 TDD；也可按事实选择测试后补或替代验证。TDD 写明公开测试接缝、首个行为和原生验证命令；其他方式写明原因和证据。本可测试却不写自动化测试的新逻辑必须随 spec 取得用户确认。

UI Slice 记录设计定位器和版本、状态、目标视口、目标代码、复用点、行为与视觉验证及停止条件，不转录完整设计数据。没有可复现基准或稳定预览状态时，将其写为实施前置或验证阻塞。

进入 implementation 时由 CLI 自动记录各仓库 baseline 和本地 binding；不手工写 `task.json.git`，不把本机 root 写入任务文档。实施中若方案不成立，先更新受影响的 PRD、决定、可选技术方案和 spec，再继续编码。
