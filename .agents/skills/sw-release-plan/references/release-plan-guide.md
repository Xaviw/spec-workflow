# 发布变更方案写作参考

## 取舍原则

本模板从正式发布变更方案的发布概况、风险评估、变更内容、实施检查和回滚结构中提炼，但服务于开发工作流内的发布交接，而不是替代生产运维流程。

- 保留能够从任务交付证据确定的变更范围、版本来源、依赖顺序、风险、验证和回滚结论。
- 省略平台点击路径、操作截图、逐分钟进度播报、会议与工单过程、具体运维命令和执行器参数。这些内容依赖正式环境与组织流程，工作流不应猜测或维护。
- 生产时间、负责人、实例、工单、正式环境版本等信息未知时留空；确认发布方案不要求用“无”或占位语填满。
- 整节确实不涉及时删除；无法从当前证据判断是否涉及时保留空白。空白和“无”语义不同。
- 信息缺口会影响范围、顺序、数据安全、验证或恢复时，不再静默留空，移入“外部补充与阻塞项”。

## 章节指引

### 发布概况

- 使用可读的迭代名称，以及证据能够支持的目标版本或批次。
- 变更背景只概括本次发布解决的问题，不复制 PRD 或技术方案。
- 影响范围写用户、功能、服务、接口、数据和运行环境中实际受影响的部分。
- 停服、灰度和计划时间只有在已有可靠决定时填写。

### 风险与依赖

- 外部依赖包括第三方发布时间、公共契约、云资源、权限申请和其他系统先后关系。
- 风险写触发条件、影响、预防或缓解措施、停止条件和应急预案；负责人和处理时点未知时可留空。
- 不把低风险写成无风险。数据不可逆、协议不兼容、资源容量不足和依赖未就绪必须显式暴露。

### 变更内容

- 已完成任务和独立简单变更用于追踪来源；面向执行的内容按仓库、服务、数据、配置和资源合并。
- 仓库表记录最终 HEAD 和 tree，并在证据存在时补版本、镜像或 Tag；不要根据分支名或 commit message 猜生产版本。
- 数据库变更说明结构、数据、安全或加密顺序、验证方式和回滚限制。可以引用已审查的 DDL artifact，但不执行 DDL。
- 配置只记录配置项名称、变更目的、前后差异或敏感值的获取方式，不记录凭据值。
- 其他资源按实际命中记录定时任务、消息队列、对象存储、CDN、搜索索引、小程序或第三方能力；不要为模板中出现的平台强行建节。
- 公共契约与联调写兼容窗口、调用方顺序和已完成的联调证据。

### 发布编排与验证

- 按依赖关系写代码、契约、数据、配置和资源的先后顺序；没有顺序要求时不虚构步骤。
- 发布前检查聚焦最终 Git 快照、备份或恢复前置、依赖就绪、关键监控基线和测试证据。
- 发布后验证使用可观察结果，覆盖核心功能、数据正确性、日志、指标、告警和必要观察期。
- 只写检查目标和通过标准，不写生产平台的逐步点击或命令。

### 回滚方案

- 写清触发条件、可回退目标、数据与配置处理、执行顺序和回滚后验证。
- 无法安全回滚时说明原因、影响和前向修复或停止策略，不用“重新发布”代替恢复方案。
- 小程序审核、数据删除、消息消费等受平台或不可逆状态限制的变化，要写清回滚边界。

### 外部补充与阻塞项

- 正式环境信息承接开发工作流无法可靠获得、但外部发布流程可能需要的时间、人员、实例、工单和操作材料。
- 未匹配 Git 变更记录未被交付 commit 覆盖的路径及其处置决定；来源不明时由用户决定。
- 阻塞项只放真正阻止范围成立、发布排序、数据安全、验证或恢复的问题，写明影响和确认责任。

## 三轮评审

1. **变更正确性**：从任务、简单变更和 Git 快照反查方案，检查变更类型、依赖、兼容性及数据顺序。
2. **协作与验证**：从开发、测试和发布交接视角检查影响范围、契约、检查项、观察项和外部缺口。
3. **风险与恢复**：从生产风险视角检查停止条件、回滚目标、不可逆变化、监控告警和人工处置边界。

评审只要求当前开发工作流能够负责的内容闭合，不以补齐生产运维手册为完成标准。
