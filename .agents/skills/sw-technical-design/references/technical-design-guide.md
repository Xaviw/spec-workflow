# 独立技术评审写作参考

## 写作原则

- 面向接口、数据、前后端协作、架构、安全和发布风险的外部评审，只写影响评审决定的结论。
- 当前证据不足但不影响结论时省略；会影响契约、安全、数据正确性或关键取舍时列为待确认问题。
- 明确区分当前约束与目标结论，不记录查找源码和比较方案的过程。
- 单任务方案可以引用实际影响结论的 AC、ADR 和项目事实；迭代汇总应将必要事实解引用，不暴露内部 task、repo 或 AC ID。

## 章节指引

- **评审范围与结论**：说明需要评审的变化、系统边界、最终选择及主要影响。
- **接口与数据契约**：写调用方、方法、URL、鉴权、字段、类型、约束、错误语义、兼容窗口，以及实际命中的分页、幂等、限流、超时、重试或回调校验。
- **前后端及跨服务关键链路**：写影响协作的状态、调用顺序、异常分支和跨端约定；只有复杂链路才使用图。
- **数据库与历史数据**：写表、字段、索引、约束、关系、迁移顺序、锁与容量风险、历史数据校验和回滚边界。
- **安全、架构与兼容性**：写可信身份、授权和数据范围、敏感数据保护、架构变化、容量边界、兼容策略及必要的配置或资源依赖。
- **关键难点、风险与待确认问题**：只写真实技术难点、方案取舍、触发条件、影响和缓解措施；可以从现有事实回答的问题不放在这里。

## 删除清单

技术方案不得包含源码文件或函数定位、逐步修改清单、TDD 或测试命令、实施停止条件、完整 AC 到步骤映射、Slice 状态、进度、内部调研记录和模板驱动的空章节。

## 评审收敛

依次检查关键技术与数据正确性、接口和前后端协作、安全与架构风险。结论一致且无阻塞未决项即可进入实施方案；测试矩阵、代码位置和实施顺序留给 `spec.md`。
