# 编写技术方案

## 上下文契约

必读：单任务读取 `task.json`、已确认的 `prd.md`、`decisions.md`、[单任务技术方案模板](references/task-technical-design-template.md)、[技术方案写作参考](references/technical-design-guide.md)和涉及仓库的说明文档。

迭代汇总必读：`iteration.json`、迭代内未取消任务的 `task.json`、已有 `technical-design.md`、[迭代技术方案模板](references/technical-design-template.md)和[技术方案写作参考](references/technical-design-guide.md)。

按需读取：单任务涉及的规范、源码、测试、配置和项目知识；迭代汇总只有在已有方案存在缺口或冲突时，才读取对应任务的 `prd.md` 和 `decisions.md`。每次扩展上下文都服务于一个明确的设计问题。

初始禁止：其他任务正文、无关仓库、完整项目知识库、实施步骤细节。

输出：单任务更新任务目录的内部 `technical-design.md`；迭代汇总更新 `iterations/<iteration-id>/technical-design.md`，并将其作为唯一对外方案文件。

## 输出边界

### 单任务

- 将 `technical-design.md` 写成工作流内部、可追踪的设计文档。允许引用 `prd.md`、`decisions.md`、ADR、项目事实、调研或 DDL artifact，并允许用 repo ID、仓库根相对路径和符号定位代码证据；行号容易漂移，仅在确有必要时使用。
- 引用用于避免重复背景和证明当前事实，不能代替目标设计。接口、字段、数据结构、关键规则、权限、异常、发布和验证结论仍写在本文件中。
- 在“验收覆盖”中直接使用 AC ID，将每项验收映射到设计章节；实际依赖的长期记忆路径使用 inline code，便于后续审阅和追踪。
- 缺少且不影响方案成立的内容留空或省略，不用猜测、“不适用”或占位语填满模板。只有阻塞设计或验收的问题才进入“风险与待确认问题”。

### 迭代汇总

- 将总方案写成脱离工作流也能独立评审的单个 Markdown 文件。正文不出现 repo ID、task ID、AC ID、源码定位或内部状态与文档引用。
- 将 task 中的引用解引用为必要事实和结论。总方案不得依赖其他文档、链接、截图或 artifact 才能理解接口、数据结构、关键规则、发布和回滚。
- 只写已有 task 方案能够支持的内容；缺失内容省略，不补造设计。服务、模块、页面、表、字段、接口和配置项等对外评审所需技术名称可以保留。

两种模式都只设计和静态审查 DDL，不执行 DDL、生产写入或其他不可逆操作，也不记录凭据值。

## 单任务流程

1. 运行 `task status <task> --json`，确认 phase 为 `technical_design`，读取已获用户确认的 PRD、仓库范围和全部验收项。
2. 围绕需求差异扫描实际入口、调用链、数据模型、复用点、信任边界和已有决定。只读取足以确认当前行为、约束和目标设计的证据；区分当前状态与目标状态。
3. 按单任务模板建立文档，并按写作参考完成命中的章节。保留全部 H2；H3 没有可靠内容时可以删除或留空。背景、目标和已确认决定优先引用上游文档，不重复转述。
4. 检查接口、字段、状态、权限、异常、发布和验证是否前后一致。认证、授权、租户、身份或数据隔离 AC 必须设计动态负向验证；静态审查只能作为补充，无法执行动态验证时应标为风险或待确认。必须由用户选择且阻塞设计的取舍调用 `grilling`，并提供访谈主题、已知事实、待决范围和以全部 AC 获得一致设计落点为完成标准；形成新术语或达到 ADR 门槛的决定调用 `sw-domain-modeling`。
5. 更新唯一的 `technical-design.md`，完成 AC 映射和实际依赖引用后，在当前任务文档和本次涉及的长期记忆有限集合内检查旧规则、已解决 Q ID 和被替代 ADR 没有继续作为当前依据。自行检查设计一致性、验收覆盖和阻塞项。等待用户明确确认后，进入 `implementation_spec` 并调用 `sw-spec`。

验证后的项目级事实和仓库事实按工作流规则同步，但不得把这些内部文件名写入对外正文。

## 迭代汇总流程

1. 采用用户明确指定或当前请求唯一选定的迭代；仍无法唯一确定时才询问。读取迭代元数据、全部未取消任务的元数据和已有技术方案；任务没有可靠技术方案时不补造内容。
2. 在已有总方案上更新；不存在时按迭代汇总模板创建。标题使用可读的迭代名称，不暴露内部 ID 或来源路径。
3. 按业务能力和技术章节重新组织，不按 task 顺序拼接。合并共同背景、流程、架构、接口、数据、安全、发布和风险，统一同一字段、状态、协议和术语。
4. 删除重复内容。方案间冲突能由已确认事实解决时统一，否则调用 `grilling`；不得静默选择。
5. 将所有必要内容写入一个总方案文件，完全空白的 H2 和 H3 可以省略。不要修改任务阶段或单任务方案；在回复中报告已纳入、缺少方案和被排除的任务，不把内部清单写进总方案。

## 评审与写法

- 按 [技术方案写作参考](references/technical-design-guide.md) 完成章节、专项扫描和三轮评审；只将实际命中的检查结果写入正文。
- 优先使用短段落、列表和 Markdown 表格。复杂关系或时序才使用 Mermaid，并在正文说明结论、边界和异常路径。
- 同一字段、状态或规则只定义一次。发现跨章节矛盾时先统一方案，再请求评审。
- 核心技术、前后端协作和项目交付视角均无阻塞问题后，技术方案才具备进入实施方案阶段的条件。

单任务阶段命令：`task phase <task> implementation_spec --confirmed`。
