# 实施任务

## 上下文契约

必读：`task.json`、`spec.md`、涉及仓库的说明和目标文件。

按需读取：`prd.md`、`technical-design.md` 的被引用章节、相关测试、DDL artifact，以及 `AGENTS.md` 规范路由命中或 spec 就地引用的文档。

初始禁止：其他任务、全部设计文档、无关仓库、未被 spec 引用的研究材料。

输出：符合 spec 的代码和测试、及时更新的任务文档、项目事实同步、代码审查和验证入口。

## 开始前

1. 运行 `task status <task> --json`，核对 phase，以及每个仓库的 canonical root、branch、baseline HEAD 和初始脏文件。完成：实施基线与已确认 spec 一致。
2. 检查既有修改、前置提交、依赖、配置和环境权限。重叠修改交由用户决定；不重叠修改经确认后排除。完成：所有前置条件满足且未 stash、reset、checkout、建分支或扩大权限。

## 实施

1. 按 `spec.md` 的仓库顺序和实施步骤执行。长任务在文档中标记已完成步骤和最近的下一步，不另建状态机。完成：当前步骤的前置条件已满足。
2. 使用目标仓库已有模式和依赖，按 `spec.md` 的测试方式实施。TDD 在已确认的公开测试接缝按纵向切片执行：写一个行为测试，确认它因目标行为缺失而失败，再写使其通过的最小实现，然后进入下一个行为；不要先批量写完测试，red 时不重构。测试描述可观察行为，预期值来自规格、已知样例或其他独立来源，不复算实现逻辑；仅在外部系统、时间、随机数、文件系统等系统边界使用 mock。完成：当前行为已形成有效 red 证据并转为 green。
3. 选择测试后补或替代验证时执行 `spec.md` 已确认的方案。UI 中可稳定隔离的状态计算、校验和数据转换优先 TDD；布局、动画和复杂交互可使用截图、浏览器检查或人工验收，并覆盖主要状态、错误态、加载态和目标尺寸。完成：当前增量代码与最小验证均通过。
4. 只产出 DDL、部署、生产写入或不可逆操作的脚本与验证方案，不执行这些动作。完成：实施没有越过环境和数据边界。
5. 发现需求、设计、spec、专业术语、ADR 或规范与事实冲突时，停止相关代码；存在必须由用户决定的未决项时调用 `grilling`，在当前请求中明确写出访谈主题、已知事实、待决范围和恢复实施所需的完成标准，再更新受影响文档与 `decisions.md` 并重新确认。涉及专业术语或关键决策时调用 `sw-domain-modeling`，不得静默改写长期记忆。每个增量完成后立即同步已失真任务文档，以及 `project/index.md` 或对应 `project/repositories/<repo-id>.md` 中已验证的当前事实。完成：任务文档、长期记忆与实现一致；写入前已重新读取现场并处理重叠修改。

## 收尾

实施中反复运行当前行为的直接相关测试，每个实施步骤完成时运行相关测试和适用的类型、lint 或构建检查。全部步骤完成后按 `spec.md` 运行一次适用的全量检查，再以 task 的 baseline Git 快照为明确范围调用 `code-review`：审查各仓库 `baseline HEAD -> HEAD/worktree` 中属于本任务的实现，排除初始脏文件及已确认的无关修改；任务文档、显式长期记忆依赖和适用约束作为审查依据。本流程处理门禁，并在修复后按同一范围复审。完成：P0 已解决或证明误报，P1 已解决或由用户明确接受并追加到 `decisions.md`，复审无阻塞。用户确认实施结果后进入 `verification` 并调用 `sw-verify`。

展示实施结果并请求进入 `verification` 时同时提示：`后续业务自测若发现与本任务相关的缺陷，直接说明现象或调用 sw-fix-bug，无需新建任务。`

阶段命令：`task phase <task> verification --confirmed`。实施阶段不提交；跨仓提交计划留到验证完成后一次确认。
